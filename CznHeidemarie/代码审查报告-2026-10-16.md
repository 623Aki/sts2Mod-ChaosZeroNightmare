### [M-2] 活的运行时 bug：空数组上调用 `Array.back()`，触发即报错并丢演出层 — 🟠 Major

- **位置**：`CznHeidemarie/effects/heidemarie_effect_groups.gd:201`（`expand_key()`）
- **问题**：第 201 行 `var last: Dictionary = rows.back()` 在**空数组检查之前**执行；而空检查在第 203 行 `if not rows.is_empty() and ...` 才做。
  - `rows` 为空的三种触发条件都真实可达：① 给了 `name` 但组里没有该骨架名（`:169-170` 的 `continue` 跳过全部层，`:171` 的 `matched` 保持 `false`）；② 组的 `spine_layers` 为空；③ 整组档但组为空。
  - Godot 4 中空数组 `back()` 返回 `null`，赋给有类型标注的 `Dictionary` 会**抛运行时错误并中断该函数**，导致调用链 `heidemarie_effect_stage.gd:271 → expand_rows:241 → expand_key` 整条崩掉——**整个特效层丢失**。
  - 更要命的是：第 221-222 行明显**本来就想优雅处理这个场景**（`if not matched: push_warning(...); return rows`），但 `:201` 的提前 `back()` 让这个保护**永远走不到**。这是**意图被自己代码破坏**的确凿 bug。
- **验证**：`expand_key` 确实在活路径上——`heidemarie_effect_stage.gd:271` `for neutral in HeidemarieEffectGroups.expand_rows(source)` → `expand_rows:241` `expand_key(key)`。
- **根因推断**：`overrides` 这块是后期（CZN_AnimLab 保存形状）追加的，追加时把 `last` 的取值提到了守卫外面。
- **正确方案**：把 `last` 的取值**移进守卫块内**——只加一行作用域改动，语义完全不变：

  ```gdscript
  # ❌ 现在（heidemarie_effect_groups.gd:201-203）
  var last: Dictionary = rows.back()
  var overrides: Dictionary = key.get("overrides", {})
  if not rows.is_empty() and overrides is Dictionary and not overrides.is_empty():
      if overrides.has("clip"):
          last["clip"] = str(overrides["clip"])
      # ...

  # ✅ 正确写法
  var overrides: Dictionary = key.get("overrides", {})
  if not rows.is_empty() and overrides is Dictionary and not overrides.is_empty():
      var last: Dictionary = rows.back()          # ← 只在有行时才取
      if overrides.has("clip"):
          last["clip"] = str(overrides["clip"])
      if overrides.has("z"):
          last["z"] = int(_num(overrides["z"], 0.0))
      if overrides.has("scale"):
          last["scale"] = _num(overrides["scale"], 1.0)
      if overrides.has("rotation"):
          last["rotation"] = _num(overrides["rotation"], 0.0)
      if overrides.has("opacity"):
          last["opacity"] = _num(overrides["opacity"], 1.0)
      if overrides.has("end_ms"):
          last["end_ms"] = _num(overrides["end_ms"], float(last["end_ms"]))
      if overrides.has("offset"):
          var xy: Array = overrides["offset"]
          last["offset_x"] = _num(xy[0] if xy.size() > 0 else 0.0, 0.0)
          last["offset_y"] = _num(xy[1] if xy.size() > 1 else 0.0, 0.0)
  ```
  **为什么这样对**：`last` 的唯一用途就是被 `overrides` 覆盖，而 `overrides` 非空必然意味着「组里至少该有一层」；把取值收进同一个 `if` 后，空 `rows` 自然走 `:221` 的 `push_warning + return rows`（原本设计的优雅降级）。行为对正常数据**零改变**。

### [M-3] 42+ 个「演出运行时」是死代码，但 profile 仍为它们填了真实配置 — 🟠 Major

- **位置**：`Integration/HeidemarieSkinProfile.cs:106-138`（`BattleReady` / `Defeat` / `Voice` / `CharacterSelect` / `RestSite` 配置）↔ `CznCore/Presentation/` 下对应读取消费者

  - `:133-138` `Voice`：4 个真实 `vo_30093_*.ogg` 路径；

  ```csharp

  // 本工程走轻量接入，Voice / Defeat / RestSite 的实际数据源在 Integration/ 下：
  //   语音 → HeidemarieCombatAudio.Voice（CharacterSkinVoicePlayerRuntime）
  //   败北 → HeidemarieDefeatCgRuntime
  // 下面这些字段没有任何 CznCore 运行时读取（读它的类未实例化），
  // 保留只会误导 —— 故置空。若将来真接入框架，再从这里恢复。
  Voice: CharacterVoiceProfile.Empty,          // 或 new CharacterVoiceProfile(...) 但加 [未接入] 注释
  Defeat: DefeatPresentationProfile.Empty,
  RestSite: RestSitePresentationProfile.Empty,
  ```
  **为什么这样对**：把「有配置但无效」变成「明显没有配置」，错误会在编译期/阅读期暴露，而不是在运行时静默失效。这也顺手让 M-1 的清理工作变得可验证。

### [M-5] `break` 误用为 `continue`：一个 cue 失败会丢弃同批剩余全部 cue — 🟠 Major

- **位置**：`CznCore/Presentation/CombatTransientEffectCueRouter.cs:244-247` 与 `:396-399`
- **问题**：两处都在 `foreach` 内，当 owner 锚点解析不到时用 `break` 跳出**整个循环**：
  ```csharp
  // :240-249（PlayForActor 路径）
  if (node2D == null) { node2D = _findOwnerAnchor(actor); }
  if (node2D == null) { break; }      // ← 应为 continue
  _queue(actor, node2D, cue, token);
  ```
  后果：只要**第 1 个** cue 拿不到锚点，后面 5 个正常 cue 全部不播——静默丢失，且无任何日志。
- **现状判定**：该类当前**零实例化**（见 M-1），因此**当前影响为 0**；但一旦按 M-1 方案 A 接入框架，它会立刻出问题。故按「潜在 bug」计。
- **根因推断**：从一段嵌套 `if/else` 里提取循环时，把「跳过本次」写成了「终止循环」。
- **正确方案**：
  ```csharp
  if (node2D == null)
  {
      WarnMissingOwnerAnchor(actor, cue);   // 建议顺带补一条日志，别静默
      continue;                             // 跳过本 cue，继续下一条
  }
  _queue(actor, node2D, cue, token);
  ```
  **为什么这样对**：同批 cue 之间彼此独立，「一条坏」不应该连坐「全批坏」；加日志则可避免「演出少一层但查不出原因」。

### [M-6] STS2 静态分析器实际未运行——工程的安全网是失效的 — 🟠 Major

- **位置**：`CznHeidemarie.csproj:29`（`Alchyr.Sts2.ModAnalyzers` 0.1.5）

## 架构评估

- **模块边界**：分层意图清晰（`CznCore` 框架 / `Integration` 胶水 / `Registration` 补丁 / `Characters` 内容），但**边界已被击穿**——`Integration/` 下 8 个文件直接调用 `ResourceLoader.Load` / `AddChild` / `QueueFree` / `Engine.GetMainLoop()` / `GodotObject.IsInstanceValid` / `CreateTimer`，而这些能力 `CznCore` **都已经提供**（`GodotNodeUtil` / `GodotScheduler`）。框架并未真正成为「唯一入口」。
- **依赖方向**：单向且健康 —— `Integration → CznCore`、`Registration → CznCore`，未见反向依赖或循环依赖。这一点值得肯定。
- **真实生效面积**：`CznCore` 约 380 个类型中，**真正被消费的只有 6 个能力簇**（`SkinEventHub`、`GodotNodeUtil`/`GodotScheduler`、`CharacterSkin{Sfx,Voice}PlayerRuntime`、`BattleReadyOverlayRuntime`、`SkinSettingsUi` 系列）。**其余约 4/5 属于参考 mod 遗留死区**（本次已逐个 grep 确认 ≥16 个类型零引用零实例化，抽样更广）。
- **主要风险**：不是「代码写错」，而是**「看起来是配置、其实是尸体」的信息失真**（M-3 / M-4 / m-4 同源）。这类问题不会报错，只会让后续每一次改动都可能「改了没反应」，是长期维护中成本最高的那一类。
- **核心建议**：**先做一次架构决断**——「真接入框架」还是「删掉未接入部分」。在此之前，不建议在 `CznCore/Presentation/` 上继续加功能；无论选哪条，都请先修 M-2（活的 bug）与 M-6（失效的分析器）。
