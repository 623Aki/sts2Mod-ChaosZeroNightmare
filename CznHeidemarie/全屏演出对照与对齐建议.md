## 1. Heidemarie 现状流程

### 1.1 触发

```
玩家打出「解放极光 / 剑之乐园」
        │
        ▼
AttackCommand.Execute
        │  Hook.BeforeAttack
        │  Hook.ModifyAttackHitCount   ← 补丁挂这里
        ▼
HeidemarieCombatPresentationPatch.TryBeginFromAttack
        │  路线绑定 / 设置开关 / 本场已起演 / 本地玩家 / 致死预判
        ▼
HeidemarieCinematicRuntime.TryPlay（:493）
        │  找施法者锚点 → 加载舞台 → room.AddChild
        │  configure(route, anchor, ownerPosition)
        │  契约校验 → 连信号 → 起 watchdog
        │  借用本体（立即隐藏或等 takeover_reached）
        └  start_stage
```

### 1.2 挂载与坐标

| 项 | 做法 | 证据 |
|---|---|---|
| 挂载父节点 | `NCombatRoom` 根 | `HeidemarieCinematicRuntime.cs`（`room.AddChild`） |
| 根节点 | `CanvasLayer`，`layer = 4090` | `heidemarie_cinematic_stage.tscn:13`；`.gd:40、130` |
| 设计画布 | 1280×720，cover 铺满并居中 | `.gd:30-32、636-645` |
| 窗口变化 | `get_viewport().size_changed.connect(_layout)` | `.gd:135` |
| z | `.cfx` 真值按名次压进 `[-4000, 4000]`，黑幕 `-4096` | `.gd:42-64` |

### 1.3 舞台内部

| 内容 | 做法 |
|---|---|
| 黑幕 | `ColorRect` 盖住战斗画面，形成接管感 |
| 世界层 | 受 `camera.moves / zooms / shakes` 影响 |
| 屏幕层 | 不受镜头影响（闪白、背景、cut-in 类） |
| 图层 | 每个 Spine 图层独立 `start_ms / end_ms / z / offset / scale` |
| 时钟 | `Time.get_ticks_usec()` 差值，自走毫秒时钟，不依赖 `AnimationPlayer` |
| 预演 | `_begin_clock` 等两次 `RenderingServer.frame_post_draw` 后才置 epoch |

### 1.4 两阶段生命周期（2026-10-18 重构后）

```text
presentation_started → 起播演出音效（C# 侧）
takeover_reached     → 延迟隐藏本体（ux 的 1233.3ms 起手）
hit_reached          → Hit 闸门放行（伤害落地）
actors_restored      → 归还本体 + Idle
stage_finished       → FinishPresentation：归还本体、Hit/Finished 放行、
                       _phase → _tail（舞台继续放余韵）
resources_finished   → End：cancel_stage + QueueFree，_tail 清空
```

| 方法 | 作用 | 位置 |
|---|---|---|
| `FinishPresentation` | 画面收尾，只放闸门、不释放 | `HeidemarieCinematicRuntime.cs:847` |
| `End` | 彻底释放，清 `_phase` / `_tail` | `:881` |
| `Watch` | 画面阶段与 tail 阶段都看门狗 | `:796` |
| `CancelFor` | 同时收 `_phase` 与 `_tail` | `:822` |
| `OnVictory` | 胜利早于收尾时延迟取消 | `:959` |
| `SuppressesBattleReady` | 演出期间压制左侧特写 | `:267` |

### 1.5 伤害与出牌闸门

| 闸门 | 谁等它 | 何时放行 |
|---|---|---|
| `Hit` | `CreatureCmd.TriggerAnim` 补丁 | 舞台 `hit_reached` |
| `Finished` | 终结牌 `OnPlay` 末尾 | 舞台 `stage_finished`（画面收尾） |

`Hit` 使用 `RunContinuationsAsynchronously`：信号在舞台 `_process` 里发，
默认内联续体会在遍历图层中途插进伤害结算。

### 1.6 音频 / 设置 / 多人

- 音频：`presentation_started` 时起播（C# 外置 ogg），取消时停，自然播完不掐尾。
- 设置：`EffectiveEffectsEnabled && ShowCardPlayPresentation`。
- 多人：`LocalContext.IsMe(player)`。

## 2. Nine 现状流程

### 2.1 触发

```csharp
[HarmonyPatch(typeof(Hook), "ModifyAttackHitCount")]
Postfix:
  → 计算攻击路线（NineAttackRoutes.Select）
  → IsCinematic(route)?
  → CombatAttackFullScreenPresentationPolicy.Allows(...)
  → NineCinematicRuntime.TryBegin(...)
       ├ 成功：WithAttackerAnim("Attack", 0f) + WithHitFx()   ← 清空原生动作与命中特效
       └ 失败：降级到 U3 路线
```

证据：`NineBasicCombatRuntime.cs:56-75`。

### 2.2 挂载

- `sceneTree.Root.AddChild(phase.Overlay, ...)`（`NineCinematicRuntime.cs:192`）——挂**根 Viewport**，不是 `NCombatRoom`；
- 根场景 `nine_cinematic_stage.tscn` 是 `CanvasLayer`，`layer = 4090`（`.gd:61`）；
- 房间销毁不会自动带走 Overlay，所以 Nine 用 `TreeExiting` + `Cancel` 矩阵兜底。

### 2.3 角色与敌人：镜像代理

Nine 是两家唯一**重新编排战场**的：

1. 施法者锚点 → `CreateProxy` 复制成 `NineCinematicOwner`；
2. 每个目标复制成 `NineCinematicTarget`，原始骨架隐藏；
3. proxy 按座位偏移放进舞台的 `target` 节点；
4. `configure` 里 `proxy.scale /= cover`，把屏幕空间归一化到 1280×720 设计画布；
5. `actors_restored` 时恢复原骨架并 `ReturnHome`。

证据：`NineCinematicRuntime.cs:125-150、223-239`；`.gd:67-76、202-210`。

### 2.4 数据模型

- 直接消费提取后的官方时间轴：`plan.layers` + `timeline.timeline`（`SETTING / SHAKE / CONTROL_ANI / WEBP / cutin`）；
- 静态 `_bundles` / `_catalog` 缓存，每条路线只解析一次（`.gd:85-120`）；
- `ux_all_attack` 的 WEBP 屏障做 `hold_ms` 时间平移（`.gd:97-112`）；
- z 用 `index - 100` 的保序压缩（`.gd:176`），黑幕 `-1000`（`.gd:145`）。

### 2.5 两阶段生命周期

```text
presentation_started → 隐藏所有被代理的原骨架
hit_reached          → Hit 放行
actors_restored      → 恢复原骨架 + Idle
stage_finished       → FinishPresentation：归还本体、_active → _tail
resources_finished   → Release：cancel_stage + QueueFree + 释放 proxy
```

`_tail` 的作用：`stage_finished` 之后舞台继续放视觉/音频余韵，
`SuppressesBattleReady` 会查 `visuals_finished` 决定是否继续压制特写
（`NineCinematicRuntime.cs:51-71、311-365`）。

### 2.6 闸门 / 胜利 / 音频 / 预演

| 项 | 做法 |
|---|---|
| 伤害闸门 | `TriggerAnim` Prefix → `TryWaitForHit(player)`（`NineBasicCombatRuntime.cs:167-180`） |
| 出牌尾巴 | `AttackCommand.Execute` Postfix → `WaitForFinish(command)`（`:299-313`） |
| 胜利 | `DeferVictory` 把胜利动作推迟到演出结束 |
| 音频 | 舞台内 `AudioStreamPlayer`；`end_ms = max(视觉结束, 音频长度)`，音频未播完不发 `resources_finished` |
| 预演 | `start_stage()` 先 `await _prime_first_draw()` 再置 epoch（`.gd:271-277`） |

## 4. 尺寸与窗口自适应（1280×720 到底是不是固定？）

### 4.1 1280×720 是**逻辑设计坐标**，不是固定像素

Heidemarie 没有 `SubViewport`、没有固定分辨率缓冲区，
舞台直接画在 `CanvasLayer` 上。`DESIGN_SIZE = (1280, 720)` 只表示：

- 时间轴里的 `x / y / offset / scale` 以这套坐标为单位；
- `owner_position` 要换算到这套坐标；
- 图层 z 与黑幕的排序与尺寸无关。

真正的像素尺寸始终等于**视口可见尺寸**：

```gdscript
var size: Vector2 = get_viewport().get_visible_rect().size
```

### 4.2 当前算法：cover（等比铺满 + 居中）

`heidemarie_cinematic_stage.gd:637-645`：

```gdscript
func _layout() -> void:
    if not is_instance_valid(_canvas):
        return
    var size: Vector2 = get_viewport().get_visible_rect().size
    if size.x <= 0.0 or size.y <= 0.0:
        return
    var cover: float = maxf(size.x / _surface_size.x, size.y / _surface_size.y)
    _canvas.scale = Vector2.ONE * cover
    _canvas.position = (size - _surface_size * cover) * 0.5
```

含义：

- `max` 保证**铺满**：宽高都不会小于视口；
- 多余的一边会被**裁切**，不会留黑边；
- 居中：`(size - 设计画布*cover)/2`；
- 窗口尺寸变化时重算：`.gd:135` 已连接 `size_changed`。

**所以结论是：已经自适应，不是固定 1280×720 像素。**
1280×720 只是「美术按这套坐标画」，实际会随窗口等比放大/裁切。

### 4.3 不同窗口比例的实际结果

游戏本体 `project.godot`：

```ini
window/size/viewport_width=1920
window/size/viewport_height=1080
window/stretch/mode="canvas_items"
window/stretch/aspect="expand"
```

`aspect = expand` 意味着 `get_visible_rect().size` **不是固定 1920×1080**，
而是按当前窗口比例展开后的逻辑尺寸（如 21:9 会变成 2560×1080）。
所以 `_layout` 拿到的就是当前窗口的真实逻辑尺寸，再被 1280×720 的设计画布 cover 一遍。

| 窗口/视口 | cover | 逻辑绘制 | 结果 |
|---|---|---|---|
| 1920×1080（16:9） | 1.5 | 1920×1080 | 完全吻合，无裁切 |
| 1920×1200（16:10） | 1.667 | 2133×1200 | 左右各裁 ≈107px |
| 2560×1080（21:9） | 2.0 | 2560×1440 | 上下各裁 ≈180px |
| 1024×768（4:3） | 1.067 | 1365×768 | 左右各裁 ≈171px |

裁掉的都是设计画布**边缘**；中心构图、角色锚点、命中位置不受影响。

### 4.4 三种可选模式

| 模式 | 公式 | 效果 | 适用 |
|---|---|---|---|
| **cover（当前）** | `max(sx/1280, sy/720)` | 铺满，裁边 | 接管演出（推荐） |
| fit | `min(sx/1280, sy/720)` | 完整显示，留黑边 | 重要内容贴边、必须全见 |
| stretch | `(sx/1280, sy/720)` 分开 | 全屏无裁切但**变形** | 一般不推荐（Spine 会拉扁） |

### 4.5 如果要改成 fit

只把 `maxf` 改成 `minf` 不够：黑幕 `ColorRect` 也在 `_canvas` 里，
canvas 缩到比视口小之后，四周会露出真实战场，接管感会被破坏。
需要额外补一层**视口尺寸的黑底**（挂在 CanvasLayer 下、不属于设计画布），
或者把黑幕拆成独立的全屏层。

### 4.6 如果要改成 stretch

```gdscript
func _layout() -> void:
    var size: Vector2 = get_viewport().get_visible_rect().size
    _canvas.scale = size / _surface_size       # 非等比
    _canvas.position = Vector2.ZERO
```

同时要把 `configure` 里的 owner 换算从「除以 cover 标量」改成「除以 `_canvas.scale` 向量」：

```gdscript
owner_local = (owner_position - _canvas.position) / _canvas.scale - _surface_size * 0.5
```

否则非 16:9 下角色锚点会偏。

### 4.7 注意事项

1. `get_visible_rect().size` 是**逻辑视口**尺寸（受项目 stretch 模式影响），
   不是物理像素；HiDPI 下物理像素不同，但布局结果一致。
2. 重要美术内容应放在 1280×720 的**中心安全区**，四周留出可裁切余量。
3. 舞台内部的 `camera.zoom` 是设计坐标里的镜头，不参与 cover 计算。
4. `z` 名次压缩与 cover 无关，窗口变化不需要重建图层。
5. 窗口在演出中途改变尺寸时，`_layout` 会重算 `canvas.scale/position`；
   图层 offset 是设计坐标，不需要重新标定。

### 4.8 Nine 完全同口径

`nine_cinematic_stage.gd:79-83`：

```gdscript
func _layout() -> void:
    var size := get_viewport().get_visible_rect().size
    var cover := maxf(size.x / 1280.0, size.y / 720.0)
    canvas.scale = Vector2.ONE * cover
    canvas.position = (size - Vector2(1280, 720) * cover) * 0.5
```

同样是 1280×720 设计画布 + cover + `size_changed` 重算（`.gd:65`）。
**两家在尺寸适配上没有差异。**

### 4.9 日志：演出开始时打印尺寸

Heidemarie 在演出开始、以及演出期间窗口尺寸变化时，会往 mod 日志输出一行布局诊断：

```text
全屏演出: 演出开始 窗口=(2560, 1440) 逻辑视口=(1920, 1080) 设计画布=(1280, 720) cover=1.5 逻辑绘制=(1920, 1080) 物理绘制=(2560, 1440) 窗口/视口=(1.333, 1.333) 画布原点=(0, 0)
```

字段含义：

| 字段 | 含义 |
|---|---|
| 窗口 | `Window.Size`，**物理像素** |
| 逻辑视口 | `stretch=canvas_items + expand` 后的**逻辑尺寸**，cover 以它为准 |
| 设计画布 | 固定 1280×720，时间轴坐标单位 |
| cover | `max(视口宽/1280, 视口高/720)` |
| 逻辑绘制 | 设计画布 × cover，单位是逻辑像素；可能大于视口（超出部分被裁） |
| 物理绘制 | 逻辑绘制 × (窗口/视口)，单位是窗口物理像素 |
| 窗口/视口 | Godot `canvas_items` stretch 的全局放大倍率 |
| 画布原点 | `(视口 - 逻辑绘制) / 2`，负值表示上下/左右被裁 |

### 4.10 为什么「窗口」和「逻辑绘制」数值不同

这是两套坐标，不是尺寸错误：

```text
窗口 2560×1440（物理像素）
        ÷ 1.333（Godot canvas_items stretch）
逻辑视口 1920×1080（逻辑像素）
        ← cover=1.5 把 1280×720 设计画布放大到 1920×1080
逻辑绘制 1920×1080
        × 1.333（引擎把整块画布放大回窗口）
物理绘制 2560×1440
```

游戏本体 `project.godot` 的基线是 1920×1080；当窗口是 2560×1440（同为 16:9）时，
Godot 保持逻辑视口 1920×1080，把整块 canvas 统一放大 1.333 倍。
所以「逻辑绘制 1920×1080」在屏幕上实际占满 2560×1440，**视觉上是吻合的**。

只有当「逻辑绘制」的宽高比与「逻辑视口」的宽高比不同时，才说明 cover 发生了裁切；
本例两者都是 16:9，`画布原点=(0,0)`，没有裁切。

实现：

- 舞台新增 `get_layout_snapshot()`（`heidemarie_cinematic_stage.gd`）；
- C# 在 `start_stage` 成功后调用 `LogLayout`，并把 `Viewport.SizeChanged` 接到同一方法；
- 旧 pck 没有 `get_layout_snapshot` 时，C# 按同一公式兜底重算，不会因为没重导资源而看不到日志；
- 释放时从 `SizeChanged` 摘掉回调，避免残留。

## 8. 一句话总结

**1280×720 只是设计坐标，不是固定分辨率**：Heidemarie 与 Nine 都用 `cover + size_changed` 铺满视口，
非 16:9 时裁边缘、不留黑边；要「完整不裁」得改 `fit` 并补全屏黑底，要「无裁切」得改 `stretch` 并同步角色锚点换算。
两家的真正差异不在尺寸，而在**是否重排敌人、音频归属、出牌尾巴绑在哪、本体何时隐藏**。
